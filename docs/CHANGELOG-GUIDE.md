# 更新日志书写规范

`CHANGELOG.md` 写给用户看。每个版本小节会由发版 CI 原样截取为 GitHub Release 说明（见 [RELEASE.md](RELEASE.md)），也可以照抄到服务端的应用内更新日志。技术细节写进提交记录和文档，不进 CHANGELOG。

## 结构

```markdown
## 1.1.0

修复了几处推送和下载问题，并新增了某某功能。

### 新增

- 新增某某功能，可以在某处使用。

### 改进

- 打开 App 的速度更快。

### 修复

- 下载大文件时偶尔失败。
```

1. **版本标题**：`## ` 加版本号，与标签一致但不带 `v`，后面不加其他文字。CI 按这一行找小节，找不到或为空时发版失败。
2. **概述**：分组前写一到两句话，说明这个版本最主要的变化。
3. **分组**：只用 `### 新增`、`### 改进`、`### 修复`，按这个顺序，没有内容的分组不写。
4. **条目**：每条以 `- ` 开头，一条一句，句号结尾。

## 待发版本

开发期间，在 `develop` 上把条目写进顶部的待发版本小节，标题直接写下一个版本号（如 `## 1.1.0`）。还没有这个小节时先建一个。发版时在 `release/` 分支上通读整理。

## 写法

写用户能感受到的变化，说清楚在哪里、有什么不同。

| 不要这样写 | 改成 |
| --- | --- |
| 修复 WebView textZoom 跟随系统字号 | 系统字体调大后，App 内文字不再额外放大。 |
| 重构 NativeWsManager 重连逻辑 | 网络恢复后更快收到新通知。 |
| 升级 AGP 到 9.4.1 | 不写（用户感受不到）。 |
| 修复若干已知问题 | 写出具体问题；确实零碎时写「修复了一些显示和操作上的小问题。」 |

不要出现：

- 文件路径、类名、接口名、配置项和命令。
- 内部术语和英文缩写（如 WebView、SDK、API、R8、壳层）。Android、Misskey 这类产品名称可以用。
- 提交前缀、PR 编号、作者名。
- 反引号、链接、图片、表格、多级列表和表情符号。

用词：称呼用户用「你」；不写「全新」「大幅」「极致」，能写数字就写数字。

## 发布前自查

- [ ] 标题是 `## x.y.z`，与标签一致。
- [ ] 有一句概述。
- [ ] 分组只用了新增、改进、修复。
- [ ] 每条一句话，句号结尾，没有路径、接口名和英文缩写。
